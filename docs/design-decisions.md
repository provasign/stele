# Design decisions

Each entry records a decision, the problem it resolves, and where it now lives. D-001 to D-024 resolve contradictions and gaps found in the review of the first design document (revision 21). D-025 to D-028 carry over the corrections from that doc's own second review. D-029 to D-032 make the design domain-neutral. D-033 to D-037 name the project and fit it into the Provasign family. D-038 to D-042 come from running the first Go implementation on the Project A registry and from the theory test. D-043 to D-047 define how a project with existing specs adopts Stele. D-049 makes every normative statement a requirement Stele must check, and sets the MVP to keeping specs checked. D-050 gives the IR the primitive types programs have; D-051 adds order, history and time; D-052 fixes the semantics the first held-out adjudication found wrong. D-053 grounds translation in a code-derived system model and embeds Grove, superseding D-037. D-054 makes what statements oblige the system's, and keeps conflicting invariants from hiding other conflicts. D-055 decides conflicts from the code. D-056 gives each registry one owner and one gate, superseding the multi-team ownership model. D-057 checks each spec change as one unit inside the spec tool. D-058 puts the owner's decisions in the coding agent, as questions; D-059 lets an entity name the operations that create it; D-060 infers what existing steps must write for a change's rules; D-061 lets a change's rules correct its own world-set terms and take precedence over statements outside the run. D-062 sets the product posture: Stele stands alone, reading code with Grove and text with `git grep`, without Prism. D-063 makes Stele learn each project from its owner, in the project's git. D-064 adds what a step produces, every other instance of an entity, and duration units. Entries marked "archived in stele-research" cite planning documents kept in the private research repository.

Status of every entry: **proposed**, pending owner review.

| D-049 | Every normative statement is a requirement the built system answers to, so the MVP goal is to keep specs checked: every statement codified in the system spec and checked with all the others for conflict, supersession and update. Only a judgment no check can decide is `informal`, and it is reviewed by its owner for each text version. A statement the IR cannot express yet is an `obligation` that names the missing construct; it counts as unchecked, against Stele rather than the spec. The IR grows to remove obligations: ordering over bounded traces, multiple instances with quantifiers, references to an earlier snapshot ("unchanged from before"), strings and records as observable values, and properties of repeated or combined operations (idempotence, atomicity), each specified by its own decision. Every check keeps a decision procedure; checks that need a bound name it in their result. The spec gate refuses a new or edited statement that is neither codified, reviewed nor recorded as an obligation; an adopted corpus records what is unchecked as debt the ratchet only lets shrink. Matching code and driving tests from the system spec are required, but Phase 2. Supersedes D-030's "tracked, never checked" level and the non-goal "arbitrary logic" | Specs are mostly written by AI agents, and agents build code from every statement and re-read old ones later, so a statement filed as `informal` and never checked still steers the code. The second bounded translation trial left 17 of 20 statements `needs_vocabulary`: baseline preservation, ordering, multiple instances, log content, idempotence and retry bounds. The design treated these as acceptable gaps; they are requirements | [02](02-goals-and-principles.md), [domain-coverage](domain-coverage.md#assurance-levels), [05](05-ir-and-semantics.md#rule-kinds), 15 (archived in stele-research) |
| D-050 | The IR has the primitive types programs have: bool, int (range optional), decimal (exact reals), enum, string (also bytes), duration and time (milliseconds), list (bounded by `maxLength`), set, map (values and present keys), optional values (`optional: true`, `none`, `isSet`), records (fields as an owned entity; dotted names), and relations to many (`many: true`, checked over `max` other instances), with `startsWith`, `endsWith`, `contains`, `len`, `has`, `m[k]` and `all`/`any`/`count`. Each type has operations the solver always decides; outside them a check may be `unknown`, reported as such. Generic spellings (`list<string>`, `map<k, v>`, `optional<t>`) are accepted so a translator writes a type in one field. Supersedes the core-tier exclusions of D-031 for strings, reals and sequences, D-032's bit-vector sets, and D-026's abstract aggregates | A spec language without strings or collections cannot hold most of what software specs say: the one-shot Project A translation left 89 of 249 statements inexpressible, about 41 for strings (routes, commands, formats), 13 for collections and instances (including K1 and K2, "other workspaces on the same node"). Leaving types out to keep checks decidable was the wrong trade: decidability is kept by restricting each type's operations instead | [05](05-ir-and-semantics.md#types), [domain-coverage](domain-coverage.md#theory-tiers) |
| D-051 | Order and time are past-time properties checked one step at a time: a clock `now` (set by the world), per-operation history attributes `ran(Op)`, `runs(Op)` and `lastRun(Op)` that running the operation updates, and `old(x)` for the value before a step. Also optional relations (`optional: true`, `isSet`, `none`), rules about every operation (`operation: "*"` or `"Entity.*"`) and `matches(s, regex)`. Future-time liveness without a deadline stays a planned bounded-trace check | The one-shot Project A run with D-050 types left 20 statements inexpressible: 7 about order and time (clone before start, every five minutes, refresh before expiry, finalize before cleanup, doubling delays), 4 needing optional relations, and one each needing an operation-wide guard and a format. History variables are the standard reduction of past-time temporal logic to state, and keep the checker's one-step semantics and its minimal conflicting sets | [05](05-ir-and-semantics.md#order-and-history) |
| D-052 | Five semantics fixes from adjudicating the held-out Project D run: (1) a permission with effect `possible` means the operation must be able to run in some situation where its guard holds with every other rule, checked by reachability; "MUST support / be able to" translates to it, `allow` only to "MUST run whenever"; (2) an unset optional value, or a value reached through an unset optional relation, equals and compares with nothing, so `x = v` implies `isSet(x)`; (3) a rule may name statements it `overrides` when its own text states the precedence ("regardless of", "per FR-005 MUST NOT apply"); the loser is weakened where the winner applies, and the precedence is shown on the rule; (4) `obligation` rules record requirements about the code or the development process, checked against the repository in Phase 2; (5) a relation's instance bound is raised to fit the largest count a rule compares it with, up to 64, and noted in the check's warnings. The translator prompt also asks for one outcome enum over separate success and failure flags and for invariants relating facts that constrain each other | Of 57 Project D conflicts, 16 were real; 18 came from "support" read as "always runs" against phase preconditions, 12 from linked facts kept independent, 3 from exceptions the text states, 2 from instance bounds below a count, 1 from an unset optional compared with a value and 1 from a process requirement modeled as a fact | [05](05-ir-and-semantics.md#rule-kinds), stele-research (Project D adjudication) |
| D-053 | Translation is grounded in a system model built from the code. Stele embeds Grove's Go package (`pkg/grove`) to read the project's types (enum variants as exclusive outcomes, struct fields, optional values), operations as ordered steps (call edges carry line positions), each symbol's source text, and graph snapshots and diffs. Spec statements are placed onto that model instead of each one inventing vocabulary. Prism is not part of Stele's pipeline; it stays the agent-facing layer. The solver stays a subprocess. Stele's build takes on cgo through tree-sitter, as Prism, Fuse and Relay already do. Projects without code fall back to `plan.md`, `data-model.md` and `design.md`. | Adjudicated Sonnet runs (2026-10-26): most false conflicts come from structure the translator never sees: step order (a rejected file is never read), exclusive outcomes, and the kind of item a statement covers. Grove's CLI does not expose variants, call lines or source text, and reading `.grove/grove.db` directly would couple Stele to Grove's schema. Embedding is how the rest of the family uses Grove. | this table; docs/07 to follow |
| D-054 | What a spec statement's state invariant obliges is controlled by the system, even when no operation writes it; only world facts, values the world sets, requests and actors stay the environment's. | D-055 | Proposed, for owner review; built as `stele hygiene` and `stele adjudicate` and evaluated on 2026-10-27 (research/bench/adjudicate/README.md: 26 of 31 held-out candidates decided, 14 of 14 checked correct, review recall not measured). | D-056 | One owner per registry: a person, or a group acting as one, named in `stele.yaml`. | D-057 | Proposed; milestone 1 (OpenSpec) built 2026-10-27 as `stele change openspec`, `stele approve` and `stele gate --require-approval`; milestone 2 (Spec Kit and Kiro feature branches, `stele change speckit|kiro --base REF`) built the same day (research/bench/change). Only changed statements are translated. The owner approves each new or changed rule once, and the approval is pinned to the statement's text hash, so re-translation never replaces an approved rule. The check runs inside each tool (a Spec Kit command, an OpenSpec validation step, a Kiro hook, a Claude Code hook) and again in CI. When a change replaces old behaviour, the replacement is written into the old spec: a MODIFIED delta in OpenSpec, an edit with a link in Spec Kit and Kiro. | D-058 | Proposed 2026-10-27. The owner decides inside the coding agent, never by reading Stele's files. Claude Code and Codex CLI come first, through a skill each.
