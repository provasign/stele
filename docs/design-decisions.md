# Design decisions

Each entry records a decision, the problem it resolves, and where it lives. An entry a later one supersedes or amends says so. A dash under Where means this table is the record.

Every entry is **proposed**, pending owner review; an entry marked built is in the code.

| D-038 | Enum and set types are written `{ type: enum, values: [...] }` | `{ type: enum[a, b] }`, used throughout the docs, is invalid YAML: the comma ends the value inside a flow mapping | [05](05-ir-and-semantics.md#types) |
| D-039 | Attributes are environment- or system-controlled (`controlledBy: system`, replaced by D-042: control follows from `writes`); a conflict is a situation with no response satisfying every active rule; the checker enumerates every minimal conflicting set | The design defined only allow/deny conflicts, while the case-study conflicts are obligations that cannot both be met; hand-made slices missed conflicts | [05](05-ir-and-semantics.md#situation-and-response), [06](06-checker.md#conflict-enumeration) |
| D-040 | `self` is the rule's subject (operation entity, `subject:`, or the unique entity matching its `self.` paths; ambiguity is an error). | D-042 | The registry is a transition system. Operations declare `writes` (everything else keeps its value), a `default`, and optionally an `effect`; state machine transitions become start-state preconditions and effects. Rules `on: op` read the state before in `when` and after in `assert`. System control is derived from `writes` and `controlledBy` is removed. The checker asks once for the state and once per operation, slicing invariants by what the operation writes | Specs state requirements about transitions ("release a resource's holds before deleting it", "when deleted, archive its holds"), which one state per attribute cannot express; the system could dodge such rules by never entering a state. Per-operation checks also give slicing from `writes` and match docs/04 effects and docs/06 invariant preservation, which D-039 had simplified away | [05](05-ir-and-semantics.md#situation-and-response), [04](04-data-model.md#operation) |
| D-041 | `implies` is an operator, lowest precedence, right-associative | World facts such as "a hold exists implies its resource exists" were written with it but the grammar lacked it | [05](05-ir-and-semantics.md#expression-grammar) |
| D-043 | Existing spec files stay the source of truth; Stele keeps a registry beside them, keyed by statement anchors with a text hash and introduction date, and syncs on every spec PR | Teams keep editing Spec Kit, OpenSpec and Kiro files and agents keep reading them; a registry that replaced them would be bypassed, and one that ignored them would drift | [08](08-workflows.md#w5-adopting-an-existing-spec-corpus), [04](04-data-model.md#rule) |
| D-044 | (Amended by D-056: the owner acknowledges open conflicts; later conflicts need a decision, since there are no waivers.) Open conflicts: an adoption baseline may record unresolved conflicts, each pinning one minimal rule set; the gate tolerates exactly those sets and blocks every other conflict | Every existing corpus examined was inconsistent, and the gate blocks any conflict, so adoption could not start | [08](08-workflows.md#open-conflicts-and-the-ratchet), [04](04-data-model.md#open-conflict) |
| D-045 | Adoption discovers candidate conflicts with an LLM review (by area, plus once condensed across areas) and models only the statements they cite; the checker confirms a candidate or leaves it not reproduced or unproved, and every candidate is triaged whatever its mark | Translating a whole corpus cost more, found fewer known conflicts and gave many more findings to triage than one review call; the checker confirms only some review findings and misses real ones, so it adds proof rather than deciding what is real | [08](08-workflows.md#w5-adopting-an-existing-spec-corpus) |
| D-046 | Triage drafts each decision from git history: the newer statement supersedes or retires the older; the owner approves, reverses or leaves it open | Newer specs never retiring older ones is the failure common to all three case studies, and the code usually follows the newer spec; applying it silently would be the hidden precedence D-001 forbids | [08](08-workflows.md#w5-adopting-an-existing-spec-corpus) |
| D-047 | Adoption ingests the current corpus with per-statement dates; it does not replay history spec by spec | Replay needs a modeling pass per spec, and triage needs only which statement is newer; replay stays an evaluation tool | [08](08-workflows.md#snapshot-not-replay) |
| D-048 | Equality and inequality between enum attributes with identical nonempty value-name sets compare names via deterministic value-wise lowering. Declaration order is irrelevant; unequal domains remain invalid | Translation spent model calls repairing status-copy expressions even though their finite domains matched exactly. Compiler lowering can express these comparisons directly while retaining distinct SMT types and checking meaning against the independent interpreter | [05](05-ir-and-semantics.md#types) |
| D-049 | Every normative statement is a requirement the built system answers to, so the MVP goal is to keep specs checked: every statement codified in the system spec and checked with all the others for conflict, supersession and update. Only a judgment no check can decide is `informal`, and it is reviewed by its owner for each text version. A statement the IR cannot express yet is an `obligation` that names the missing construct; it counts as unchecked, against Stele rather than the spec. The IR grows to remove obligations: ordering over bounded traces, multiple instances with quantifiers, references to an earlier snapshot ("unchanged from before"), strings and records as observable values, and properties of repeated or combined operations (idempotence, atomicity), each specified by its own decision. Every check keeps a decision procedure; checks that need a bound name it in their result. The spec gate refuses a new or edited statement that is neither codified, reviewed nor recorded as an obligation; an adopted corpus records what is unchecked as debt the ratchet only lets shrink. Matching code and driving tests from the system spec are required, but Phase 2. Supersedes D-030's "tracked, never checked" level and the non-goal "arbitrary logic" | Specs are mostly written by AI agents, and agents build code from every statement and re-read old ones later, so a statement filed as `informal` and never checked still steers the code. Most statements the IR could not express were about baseline preservation, ordering, multiple instances, log content, idempotence and retry bounds. The design treated these as acceptable gaps; they are requirements | [02](02-goals-and-principles.md), [domain-coverage](domain-coverage.md#assurance-levels), [05](05-ir-and-semantics.md#rule-kinds) |
| D-050 | The IR has the primitive types programs have: bool, int (range optional), decimal (exact reals), enum, string (also bytes), duration and time (milliseconds), list (bounded by `maxLength`), set, map (values and present keys), optional values (`optional: true`, `none`, `isSet`), records (fields as an owned entity; dotted names), and relations to many (`many: true`, checked over `max` other instances), with `startsWith`, `endsWith`, `contains`, `len`, `has`, `m[k]` and `all`/`any`/`count`. Each type has operations the solver always decides; outside them a check may be `unknown`, reported as such. Generic spellings (`list<string>`, `map<k, v>`, `optional<t>`) are accepted so a translator writes a type in one field. Supersedes the core-tier exclusions of D-031 for strings, reals and sequences, D-032's bit-vector sets, and D-026's abstract aggregates | A spec language without strings or collections cannot hold most of what software specs say: strings (routes, commands, formats), collections and other instances ("other resources on the same node") were the largest groups of statements the IR could not express. Leaving types out to keep checks decidable was the wrong trade: decidability is kept by restricting each type's operations instead | [05](05-ir-and-semantics.md#types), [domain-coverage](domain-coverage.md#theory-tiers) |
| D-051 | Order and time are past-time properties checked one step at a time: a clock `now` (set by the world), per-operation history attributes `ran(Op)`, `runs(Op)` and `lastRun(Op)` that running the operation updates, and `old(x)` for the value before a step. Also optional relations (`optional: true`, `isSet`, `none`), rules about every operation (`operation: "*"` or `"Entity.*"`) and `matches(s, regex)`. Future-time liveness without a deadline stays a planned bounded-trace check | With D-050's types, the statements still inexpressible were mostly about order and time (clone before start, every five minutes, refresh before expiry, finalize before cleanup, doubling delays), then optional relations, an operation-wide guard and a format. History variables are the standard reduction of past-time temporal logic to state, and keep the checker's one-step semantics and its minimal conflicting sets | [05](05-ir-and-semantics.md#order-and-history) |
| D-052 | Five semantics fixes: (1) a permission with effect `possible` means the operation must be able to run in some situation where its guard holds with every other rule, checked by reachability; "MUST support / be able to" translates to it, `allow` only to "MUST run whenever"; (2) an unset optional value, or a value reached through an unset optional relation, equals and compares with nothing, so `x = v` implies `isSet(x)`; (3) a rule may name statements it `overrides` when its own text states the precedence ("regardless of", "per FR-005 MUST NOT apply"); the loser is weakened where the winner applies, and the precedence is shown on the rule; (4) `obligation` rules record requirements about the code or the development process, checked against the repository in Phase 2; (5) a relation's instance bound is raised to fit the largest count a rule compares it with, up to 64, and noted in the check's warnings. The translator prompt also asks for one outcome enum over separate success and failure flags and for invariants relating facts that constrain each other | Most reported conflicts were false. In order of frequency they came from "support" read as "always runs" against phase preconditions, linked facts kept independent, exceptions the text states, instance bounds below a count, an unset optional compared with a value, and a process requirement modeled as a fact | [05](05-ir-and-semantics.md#rule-kinds) |
| D-053 | Translation is grounded in a system model built from the code. Stele embeds Grove's Go package (`pkg/grove`) to read the project's types (enum variants as exclusive outcomes, struct fields, optional values), operations as ordered steps (call edges carry line positions), each symbol's source text, and graph snapshots and diffs. Spec statements are placed onto that model instead of each one inventing vocabulary. Prism is not part of Stele's pipeline; it stays the agent-facing layer. Stele's build takes on cgo through tree-sitter, as Prism, Fuse and Relay already do. Projects without code would fall back to `plan.md`, `data-model.md` and `design.md` (not built). (Amended by D-055 and D-062: code is evidence for conflict questions rather than translation context, and Grove is opt-in.) | Most false conflicts come from structure the translator never sees: step order (a rejected file is never read), exclusive outcomes, and the kind of item a statement covers. Grove's CLI does not expose variants, call lines or source text, and reading `.grove/grove.db` directly would couple Stele to Grove's schema. Embedding is how the rest of the family uses Grove. | — |
| D-054 | What a spec statement's state invariant obliges is controlled by the system, even when no operation writes it; only world facts, values the world sets, requests and actors stay the environment's. State invariants that conflict are reported in the state unit and left out of the steps. A rule that never applies because statements' invariants rule out its situation is reported, and its step is checked again without those invariants. | Two contradicting statements normalized onto one attribute no operation writes became environment assumptions: they silently ruled out every state they constrain, and that hid another real conflict (D-042 made control follow writes only) | [05](05-ir-and-semantics.md); internal/ir requirementOutputs, internal/checker |
| D-055 | Built as `stele hygiene` and `stele adjudicate`. Conflicts are found and decided before anything is translated. The pipeline is: import with each statement's date and introducing change (git); a deterministic structural pass (one requirement title stated twice with different bodies, spec or change folders out of place, statements naming config keys or symbols the code lacks); an LLM review that proposes candidate conflicts; code evidence per candidate (text search, tests first; D-062); and one LLM verdict per candidate that cites file:line: newer statement followed (retire the older), older over-broad (narrow it), older followed (possible code bug or unfinished change), resolved in the text, no code or neither followed, or unclear. Translation, bridge, check and verify run only for candidates the code cannot decide, translating against the review's situation. Amends D-053: code is evidence for a verdict, not context for translation. (Prism part superseded by D-062: the evidence comes from `git grep` and, opt-in, Grove.) | Translating everything found few real conflicts. In the case studies, nearly every known conflict could be decided from the code and the statements' dates alone: usually the code follows the newer statement (the older is superseded or over-broad), sometimes the older (a bug in the code). Code context in the translation prompt did not help | [08](08-workflows.md#the-review-first-pipeline) |
| D-056 | One owner per registry: a person, or a group acting as one, named in `stele.yaml`. The owner approves each rule (its English rendering and examples), each vocabulary change, each decision and the adoption baseline. There are no per-context approvers, no product-owner, analyst or context-owner roles, and no exports, ownership checks, orphan checks, waivers, lock files, imports or federation. Contexts stay as namespaces: they group vocabulary and scope in-context precedence (D-001). There is one gate: `stele gate`, run by the git pre-commit hook (and in CI on pull requests, planned), blocks a spec or code change that adds a conflict, an unapproved rule or a stale rule. Code that leads its spec is reported, not waived. Ownership features return only when a project with several teams needs them | The design assumed teams with separate contexts, approvers and repositories (D-002, D-006, D-008 to D-010, D-019 to D-021). Every project studied has one owner or one maintainer group, and the extra approvals would make the gate a bottleneck before it has shown its value | [08](08-workflows.md), [09](09-enforcement.md) |
| D-057 | Built as `stele change openspec`, `stele change speckit --base REF` and `stele change kiro --base REF`, `stele approve` and `stele gate --require-approval`. A spec change is checked as one unit, in the spec tool's own terms: an OpenSpec change folder (ADDED, MODIFIED and REMOVED requirements), or a Spec Kit or Kiro feature folder. Only changed statements are translated. The owner approves each new or changed rule once, and the approval is pinned to the statement's text hash, so re-translation never replaces an approved rule. The check runs inside the coding agent (Claude Code, through a skill and hooks) and again at the gate. When a change replaces old behaviour, the replacement is written into the old spec: a MODIFIED delta in OpenSpec, an edit with a link in Spec Kit and Kiro. Planned: a code PR re-runs the code verdict (D-055) for rules whose evidence lies in the files it changes; tests generated from rules come last | W1 assumed a PR with two approval gates and whole-corpus translation. With approved rules, the useful moment to check is when a change is written. Stale older statements that newer ones replaced without retiring them were the failure in every case study | [08](08-workflows.md#w1-a-spec-change-to-approved-rules) |
| D-058 | Built. The owner decides inside the coding agent, never by reading Stele's files: Claude Code, through a skill. The agent runs `stele change --json`, reads the result, and asks the owner only what needs a person, in the spec's words, never in symbols: whether a new term means the same as an existing one, which of two conflicting requirements wins, and a final approval of the checked requirements. A new term with no near match is accepted without a question. Each answer is recorded with `stele change answer`, and only what the answer affects is translated again; Stele's own misreadings (a requirement whose rules contradict each other) are re-read once on the agent's answer before the owner is asked. `report.md` stays as the audit record. `stele gate` is the backstop: a commit with something unapproved names what is missing and points back to the agent. A new term is a conservative extension and is approved with the rules that use it, with no separate approval; a vocabulary change that alters approved rules becomes a question. Built as `stele change --json`, `stele change answer` and the `stele-change` skill (integrations/skills) | The change flow assumed the owner reads report.md and edits files by hand, which nobody does. A change needing new vocabulary adds decisions, so where the owner makes them decides whether the loop is used | [08](08-workflows.md#w1-a-spec-change-to-approved-rules) |
| D-059 | Built. An entity may name the operations that create it (`createdBy`). A creating operation writes every attribute of the entity the world does not set, so no earlier state carries over and invariants are checked on the new instance alone. During `stele change`, a clash inside one step that a state invariant takes part in becomes a `creates` question for the agent, which decides from the spec and code whether the step only ever makes a new instance (a re-initialize scenario means it does not). Its answer is recorded with the change as `createdBy`; the resulting write and controller changes are not asked again | Invariant preservation checks each step from every state the invariants allow, including an existing instance for a step that in fact creates one, which raised owner questions that came only from that | [04](04-data-model.md#operation), [05](05-ir-and-semantics.md) |
| D-060 | Built. When a change's rule asserts something about the state after a step the registry already declares, the step writes it, unless the world sets it or it belongs to another entity; `stele change` records this as `extend: Entity.op` with `writes`, and the resulting write and controller changes are not asked of the owner, since the change's own text implies them. Formalize already inferred writes for the steps it proposes | A change mostly adds rules to existing steps. A rule constraining something a step cannot change makes the step impossible, which came back as the requirement contradicting itself | [04](04-data-model.md#operation) |
| D-061 | Built. Two more of the change's own modelling choices yield to its rules. (1) A term the change proposes as set by the world, which a rule of the change fixes to a value after a step (`self.status = archived`), becomes system-set and written by that step: the requirement says the system sets it. Only the change's own terms and only an explicit `attribute = value`, so clocks and the registry's world values keep their meaning. (2) A rule may take precedence over any statement of the spec it names (FR-003b), not only over those translated in the same run. Also: two new names for one thing within a change are asked of the agent, and a conflict can be answered "that situation cannot happen", which the translator gets as a note | A world-set value that the change's rules fix made those requirements contradict themselves, and an exception written into the spec was dropped because the statement it named was not re-translated | [08](08-workflows.md#w1-a-spec-change-to-approved-rules) |
| D-062 | Stele stands alone: a user installs only `stele` and Claude Code. Stele reads code with Grove's embedded package (symbols, types, steps, references) and reads text with `git grep` (config, docs, CLI help, fully qualified uses Grove misses, languages Grove does not index). Prism is not used by Stele, as a process or a library: it is tuned for coding agents. Rule slices for agents come from Stele itself (CLI and skill); a Prism integration, if any, reads from Stele and stays optional. Specs are searched in Stele's own registry; with no code at all, Stele works on the specs alone. When Prism is installed too, both use the repository's `.grove/grove.db`: Stele pins the same Grove version as Prism and reuses an index Prism keeps. Code evidence searches text by default; Grove is opt-in (`--graph`). Conflict questions carry what the code does (`code`) and recommend the answer it follows. | Product posture. Grove alone misses callers and indexes no assembly, so text search is required beside it; Prism covers that, but making Stele depend on an agent-tuned tool would tie it to a second product. The Grove skeleton as prompt context did not reduce false conflicts, and Grove definitions did not improve code verdicts while costing more, so text search is the default. With Prism installed beside Stele, the agent runs the same loop and Grove shares Prism's index. Grove's remaining case is what text search cannot give: mapping a code change to the rules it touches, and types and steps for translation. | — |
| D-063 | Built. Stele learns each project from its owner. An owner's answer in `stele change` (two terms are one, a situation cannot happen, a requirement was misread) is saved as a lesson, one file under the registry's `lessons/`, written to the change's head registry so approving the change commits it; `stele lesson add` records one directly. Every later translation and coverage check in the project reads the relevant lessons; a pinned lesson stops applying when its requirement's text changes. Lesson IDs hash their content and the approval ledger is one file per run, so parallel branches merge without conflict. Only the owner's answers teach; the agent's own corrections do not. Learning stays in the project: nothing is shared across projects. | Readings depend on judgments only the owner can make: the owner overturns readings a model judged faithful. Answers kept in an uncommitted work directory and pinned to one statement would leave the next change, a teammate or CI without them. Files in the registry give history, review in PRs, revert and merging for free. | [04](04-data-model.md#lesson), [08](08-workflows.md#w1-a-spec-change-to-approved-rules) |
| D-064 | Built. Three constructs close the grammar gaps the case studies show most often. (1) `result`: what a step produces (returns, messages, notifications, events, logs, metrics, attempts) as attributes of a built-in `Result` entity, extended like `Request`; in the step it is part of the response with no frame, and it may be read only in the `assert` of a rule on an operation. (2) `instances(E)`: every other instance of an entity, as a relation to many the loader adds when a rule uses it (never written to files); global uniqueness and counts across all instances. (3) `seconds`, `minutes`, `hours`, `days` (a whole number as a duration), `min`, `max`, `abs`: linear and exact. The translator and vocabulary prompts teach them, and the patterns already expressible (order through history, validation as a precondition on a request fact, references as optional relations, "both succeed or both roll back" through `result` and `old`). Deferred, each still an obligation: future-time order over bounded traces, idempotence of repeated operations, non-linear arithmetic, graph traversal, geometry, merge semantics | Outputs, ordering and retries, and aggregates over all instances were the most common gaps; each needs a decision procedure, and these three keep the check in linear arithmetic over bounded instances | [05](05-ir-and-semantics.md#what-a-step-produces), [05 aggregates](05-ir-and-semantics.md#aggregates) |
