This project keeps its requirements as Markdown under `{{root}}/`, and you write them. A request is a task, and Stele says nothing about it. Write a requirement before you build only when the owner asks for something the product must keep ("from now on", "always", "never", or a default or limit the product keeps), never for a one-off job (a review, a trial, a write-up, a fix, a measurement). A request worded as a job ("add a return command; only the holder can return a packet") is a task even when it names a rule: build it, then offer once, in one line, to write the rule down as a requirement so Stele guards it. Write each requirement as one list item in the file for its area (`{{root}}/<area>.md`), starting with an ID no other requirement has (`REQ-001`) and saying what must be true with MUST, MUST NOT or SHOULD, worded as the owner would; leave out how it is built (files, stores, budgets, "tests included"), since Stele reads every clause as a requirement the product keeps. Then, before the first edit of code, run the check (step 1) and follow the steps above. The project's first requirements are checked the same way: there is nothing to adopt. A check that reads new requirements takes a few minutes: wait for it to finish and read its JSON before you edit anything, and edit only once the owner has approved. To change or drop a requirement, edit or delete its line, showing the owner the new wording, and run the check again: Stele asks the owner what a change to an approved requirement means. Commit `{{root}}/` and the registry with the code.
